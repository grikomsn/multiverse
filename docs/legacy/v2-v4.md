## Cross-cutting recommendation

| Version                                   | Recommendation                                                                              | Effort |
| ----------------------------------------- | ------------------------------------------------------------------------------------------- | ------ |
| v2 (2018, Next 7 + Bulma + EmojiOne)      | **B**: Astro port with frozen 2018 data. Reuse most of the `M26/apps/web-v2` UI components. | S–M    |
| v3 (mid-2019, Gatsby + Bulma + blog)      | **B**: Astro port with frozen JSON and markdown. Fall back to **D** if time is short.       | M      |
| v4 (late 2019, Gatsby + Tachyons + Inter) | **B**: Astro port with frozen 2019 data. Reuse the `M26/apps/web-v4` shell.                 | S      |

Why B rather than A for all three:

- The new schema has no version-specific singletons. Option A would bring back `webV2Site`/`webV4Site`-style documents and `webV2` namespaced fields on shared types.
- The multiverse-2026 experience shows what A produces: 2026 content (Graz, Bluesky, "Senior Product Engineer, Tangerang") inside a 2018/2019 layout. That defeats the purpose of a "past versions" archive.
- Each version's content is small, ranging from about 1 KB of JSON to 4 markdown posts. Freezing it in `src/data/*.ts` is cheap and has no drift.

Why not C:

- Every version needs Node 10–12.
- Two of the three use node-sass 4 (`V2`: 4.10.0; `V4/legacy/v3`: 4.12.0), and sharp 0.22/0.23 is also involved. None of these has prebuilt binaries for darwin-arm64.
- So C means pinned `linux/amd64` Docker images, a dead registry ecosystem, and service workers that must be stripped.
- The output still would not be faithful, because v2's `/open-source` pulls live GitHub data at build time.

Suggested structure:

- **One Astro app per version** (for example `apps/archive-v2`, `apps/archive-v3`, `apps/archive-v4`). Each version ships a conflicting global CSS framework (Bulma 0.7.2, Bulma 0.7.5 with SCSS overrides, Tachyons 4.11) and a different base font. Bundling them into one app would require scoping all three frameworks.
- Use Astro `base` if the hosting decision is path-based (`/v2/…`). All internal links in the frozen data must go through a `withBase()` helper. Today `/socials`, `/about`, `/contact` and the like are hard-coded absolute paths.
- Add one small shared "archived version" banner. `V4/legacy/v2/components/LegacyNotice.js` already did this in 2019: a dismissible Bulma notification that remembers dismissal in `sessionStorage`. Reproduce it in each archive's own CSS so it doesn't import the new design.
- Under B the only optional CMS touchpoint is a `site` document per archive property (title, url, SEO), if the archive index page should list versions from Sanity. The version content itself stays in code.

## v2: Next.js 7 + Bulma 0.7 + EmojiOne 4 (2018)

### 1. TL;DR

This is a single-page yellow/dark Bulma landing page. It has the hand-lettered "Griko Nibras" sticker wordmark, a contact modal, a `/socials` grid of 18 brand-colored tiles, and an `/open-source` page that called the GitHub API at build time. All copy is hardcoded JSX. Two Wayback captures (2018 and 2019) confirm the text. **Recommend B**: rebuild on Astro with the 2018 copy frozen. Most of the existing `M26/apps/web-v2` markup and vanilla-JS navigation can be reused. Swap its Sanity data layer for static data, and pin Bulma 0.7.2 CSS and Font Awesome 5 brand icons.

### 2. Overview

- **Era:** Nov 2018 to mid-2019 on griko.id.
  - `package.json` is version `2.0.0`, all files are dated 2018-11-12, and the footer copyright shows 2018 in the Wayback capture.
  - In 2019 it was refactored to `V4/legacy/v2`: Next 9.0.3, function components, styled-components. The `/open-source` page was removed and a legacy toast added. That copy was served at **v2.griko.id** (`V4/legacy/v2/now.json`).
  - The v3 and v4 sites redirected visitors arriving from `bulma.io/expo` to v2.griko.id (`V4/gatsby-browser.js:8-10`). The README says the site was featured on Bulma Expo.
- **Stack:** Next 7.0.2 with a custom `server.js` that serves the service worker, React 16.6, Bulma 0.7.2 via `@zeit/next-sass` and node-sass 4.10.0, EmojiOne 4.0.0 SCSS map, Font Awesome 5.5 (react-fontawesome), react-reveal, react-lazyload, next-page-transitions, next-offline, next-optimized-images, next-purgecss, and `@octokit/rest` 15.
- **Deploy:**
  - Static `next export`. Then `post-export.js` writes `out/CNAME = griko.id` and `.nojekyll`, left over from GitHub Pages.
  - The README says it was hosted on Netlify. The footer says "Hosted on Netlify".
  - The 2019 copy was hosted on ZEIT Now (`@now/static-build`, `distDir: out`).
- **Original domain:** `griko.id`, later `v2.griko.id`. According to project memory, griko.id is now someone else's site.

### 9. Risks and open questions

- **GitHub token in the client bundle (2018):**
  - `V2/next.config.js:140-143` injects `GITHUB_TOKEN` into the **client** webpack bundle through `EnvironmentPlugin`.
  - `pages/open-source.js:886-890` reads it in `getInitialProps`, which also runs in the browser during client-side navigation. So the token the owner used for the 2018 deploy was very likely shipped in public JS.
  - Confirm that the token was revoked. Never reintroduce this pattern.
- **`/open-source` content is unrecoverable** from Wayback. Options:
  - (a) Freeze a hand-curated list of pre-Nov-2018 non-fork repos, with today's star counts or no counts.
  - (b) Reuse the authored repos from v3's `open-source.json`.
  - (c) Show a static note linking to GitHub.
- **Dead contact data:** `hello@griko.id` and `griko@protonmail.com`, plus fb.me, LINE, Gravatar and similar links. Decide whether to keep them verbatim (historical) but render mailto links as plain text, and add a banner pointing to nibras.co.
- **EmojiOne license** for self-hosting, and the jsDelivr `/emojione/` legacy path disappearing someday. Self-host either way.
- **Which v2:** the 2018 original (Netlify, `/open-source`) or the 2019 `v2.griko.id` copy (no `/open-source`, legacy toast)? This report assumes 2018.
