# Motion inspiration (late 2026)

Research for the nibras.co motion system, gathered 2026-11-15. The brief: learn how the latest Framer showcase sites do playful, illustrative motion, then translate it to our stack (Astro 7 static output, Tailwind 4, Cloudflare Workers) **without** a Framer or React runtime. The visual direction is [design.md](../design.md): cream paper, thick navy ink outlines, halftone dots, tilted cards, speech bubbles, a route rail, seat grids and geometric characters.

How things were checked:

- **Verified** means the site was opened in a browser on 2026-11-15 (Chromium, 1280×800, no throttling). On load I read `document.getAnimations()`, Resource Timing, LCP and CLS, and inspected inline transforms while scrolling. Mobile Lighthouse 12.8.2 runs on the same day used Playwright's `chrome-headless-shell` with default mobile throttling. The keyless PageSpeed Insights API returned HTTP 429.
- **Described** means the information comes from Awwwards, Framer Gallery or roundup write-ups only, without opening the site.
- Library sizes in §2 were measured directly: `bun build --minify`, then `gzip -9`, on the package versions listed there.

## 1. References

### How Framer sites actually move (observed)

- **Appear effects** (fade/slide/scale on load) are WAAPI/CSS animations on the document timeline. Shelby's Desk had 134 running `CSSAnimation`s at idle, animating only `opacity`, `translate`, `scale` (plus 6 `box-shadow`).
- **Scroll effects** (parallax, scroll-linked rotation, "while in view") are written by Motion's JS loop as inline `style.transform` every frame. On the Stickers page, 140 elements carried inline transforms like `perspective(1200px) translateY(-50%) translateX(-141.7px) … rotate(0deg)`, and 11 of the first 40 changed during a 900px scroll. `getAnimations()` saw none of these. This is the part we replace with native `animation-timeline`.
- **Springs** come from the Motion runtime (stiffness/damping); we approximate them with CSS `linear()` (§4).
- **Rich illustration motion** is Rive or Lottie. Huy Phan's console logged a Rive artboard error, and YES NOW loaded `dotlottie-player` (258 KB) plus about 10 Lottie JSONs.
- **Baseline cost**: every Framer site shipped 315–790 KB of JS, plus React hydration warnings on 3 of 6 (`Minified React error #425/#422`).

## 3. Performance rules

**What the references teach (mobile Lighthouse 12.8.2, default throttling, 2026-11-15):**

| Site           | Perf | LCP    | TBT    | CLS   | Weight   | Notes                                                      |
| -------------- | ---- | ------ | ------ | ----- | -------- | ---------------------------------------------------------- |
| Sandra Creates | 97   | 2.6 s  | 0 ms   | 0     | 631 KB   | SVG character, little motion                               |
| Mila           | 73   | 7.9 s  | 60 ms  | 0.003 | 2.2 MB   | Photo LCP; 10 non-composited animations (`left`, `filter`) |
| Shelby's Desk  | 61   | 9.4 s  | 10 ms  | 0.002 | 2.3 MB\* | PNG illustration LCP, no `fetchpriority`; 9.1 s JS bootup  |
| YES NOW        | 52   | 4.1 s  | 130 ms | 0.828 | 3.2 MB   | 8.6k DOM nodes on mobile; Lottie layout shifts             |
| Huy Phan Vol.2 | 18   | 12.8 s | 134 s† | 0.342 | 2.4 MB   | Rive/WebGL canvas; LCP is an absolutely positioned div     |

\* About 7 MB on desktop after lazy images load. † Headless software rendering inflates canvas work, but it is still the worst by far. This matches 2026 reports that unoptimized Framer sites sit around 40–65 on mobile PageSpeed. The JS runtime sets a floor; images and canvas/Lottie push them below it.

The lesson: **the motion itself was never the bottleneck.** Heavy raster illustration, layout-animating properties, and canvas/WASM runtimes were. Motion on compositor properties is nearly free.

**Rules for nibras.co**

1. **Animate only `transform`, the individual `translate`/`rotate`/`scale` properties, and `opacity`.** `clip-path` and `filter` only on small elements. Never `top/left/width/height/margin`. Lighthouse's `non-composited-animations` audit must be empty. Our `.ink-hover` transitions `box-shadow`, which repaints a small box and is acceptable. For large cards, move the shadow onto a `::before` (an ink-filled copy offset with `translate`) and animate that.
2. **Don't stack incompatible animations on one element.** "Target has another animation which is incompatible" was the top Lighthouse failure on both Shelby and Mila. Put the scroll-driven entrance on a wrapper and hover/press on a child, as the comment already says for `.settle`.
3. **`will-change` only while animating** (e.g. during drag). Shelby left 27 elements promoted permanently.
4. **No layout thrash:** no scroll listeners. Scrubbed effects use `animation-timeline`; one-shots use a trigger or `inView`. In the few scripts, read layout once and write `transform` in rAF.
5. **`content-visibility: auto` + `contain-intrinsic-size: auto 800px`** on below-the-fold sections (Baseline since Safari 18, Sept 2025). Skip it on sections with sticky scenes or anchor targets you've measured as broken.
6. **Never fade the LCP element from `opacity: 0`.** LCP isn't recorded until it's visible. Entrance on the hero should be transform-only, or apply to decorations, not the headline. The hero illustration is inline SVG or a preloaded AVIF with `fetchpriority="high"`; Shelby's PNG with no priority hint cost it an LCP of 9.4 s.
7. **Budgets (p75 field / mobile lab):** LCP ≤ 2.0 s (Google "good" is ≤ 2.5 s); INP ≤ 150 ms (good ≤ 200 ms); CLS ≤ 0.02 (good ≤ 0.1); motion JS ≤ 10 KB gz on the home page and **0 KB on reading pages**; home transfer ≤ 500 KB excluding fonts; DOM ≤ 1,500 nodes; mobile Lighthouse ≥ 95.
8. **Islands only when needed.** Most motion is CSS. For behavior, use a plain `<script>` in the Astro component (bundled as a deferred module, deduped across instances). Use a framework island only for real UI state (e.g. the seat-picker game), with `client:visible`, or `client:idle` for below-fold interactive bits, and `client:media="(pointer: fine)"` for cursor toys.
9. **Images:** `astro:assets` `<Picture>` with AVIF/WebP and explicit `width`/`height` (no CLS). Illustrations are SVG, optimized with svgo; inline them only when parts animate, otherwise use `<img src=".svg">` so they're cacheable. Frame-by-frame loops use `steps()` sprite sheets or a `<video>` with `preload="none"` and a poster.
10. **Fonts:** Astro Fonts API with the local provider (already configured). Keep its generated metric-adjusted fallbacks (`size-adjust`, `ascent-override`) to avoid swap CLS, `font-display: swap`, and preload only the display serif used in the hero. Subset if the licence allows.
11. **INP:** interaction handlers only toggle classes or attributes; CSS does the animating. No heavy work in `pointermove`. View transitions on navigation stay ≤ 300 ms.
12. **Reduced motion means reduced, not removed:** keep opacity crossfades and state changes, drop translation, rotation, parallax and loops. Consider an in-page "motion" sticker toggle (`data-motion="reduce"` on `<html>`, `localStorage`) as a user override on top of the media query.
